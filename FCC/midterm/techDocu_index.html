Introduction

Git tracks changes to a set of files over time. Instead of saving one file at a time, it records the full state of a project as a series of snapshots, so you can move backward and forward through the history of what you built.

Unlike tools that keep a single shared history on a server, Git gives every clone of a project its own complete copy of that history. You can commit, branch, and inspect the past entirely offline, and sync with others only when you choose to.

This page walks through the commands you will reach for most often: setting up a repository, saving work, branching, collaborating through a remote, and reversing mistakes.

Getting a Repository

There are two common starting points: turning an existing folder into a repository, or copying one that already exists somewhere else.

Run the following inside any project folder to begin tracking it:

git init

To download a full history from somewhere else, use clone instead of starting from scratch:

git clone https://example.com/team/project.git
  • A fresh git init repository has no commits yet.
  • A cloned repository arrives with the entire commit history already present.
  • Both approaches produce an ordinary working copy, so there is no difference afterward.
The Basic Workflow

Git separates the act of editing a file from the act of recording that edit. Changes move through three stages: the working directory, the staging area, and the committed history.

Check which files have changed and which stage they're in at any time:

git status

Move a changed file into the staging area, then record it permanently:

git add notes.md
git commit -m "Add first draft of the notes"

A message that explains why a change was made is far more useful later than one that only restates what changed.

The full timeline of commits can be viewed with:

git log --oneline
Branching and Merging

A branch is simply a movable pointer to a commit. Creating one lets you try an idea without touching the work everyone else sees.

git branch experiment
git switch experiment

Once the work on a branch is ready, bring it back into the main line of development with a merge:

git switch main
git merge experiment

Most merges combine automatically. Occasionally the same lines were changed on both branches, producing a conflict that Git cannot resolve on its own, and the file must be edited by hand before it can be committed.

  • Branches are cheap to create and cost no real disk space up front.
  • Deleting a branch after it's merged keeps the branch list readable.
  • A branch name is just a label; the commits it points to are what actually matter.
Working with Remotes

A remote is a version of your repository hosted somewhere else, most often a shared server that your collaborators also connect to.

List the remotes a repository already knows about:

git remote -v

Send local commits to the remote so others can see them:

git push origin main

Bring down commits made by others and merge them into your current branch:

git pull origin main

If your local history and the remote's have both moved forward independently, a plain pull may open a merge. Many teams prefer to rebase instead, which replays local commits on top of the latest remote history.

Undoing Things

Mistakes are routine, and Git offers several ways to walk them back depending on how far the change has traveled.

Discard edits to a file and return it to its last committed state:

git restore notes.md

Create a new commit that reverses an earlier one, leaving history intact:

git revert a1b2c3d

git reset --hard rewrites history and discards work permanently, so revert is usually the safer choice once a commit has already been shared with anyone else.

Good Habits

A few habits tend to separate a repository that's pleasant to work in from one that's a chore to untangle later.

  • Commit small, focused changes rather than one enormous batch at the end of the day.
  • Write commit messages in the present tense, as an instruction: "Fix off-by-one error," not "fixed."
  • Keep a .gitignore file so build artifacts and local settings never get committed by accident.
  • Pull before you start new work to reduce the odds of a conflict later.

None of this is enforced by the tool itself. Git is happy to let a history be as messy as you allow it to be, so the discipline is entirely up to the people using it.
